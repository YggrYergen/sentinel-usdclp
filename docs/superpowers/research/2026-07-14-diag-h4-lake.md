# Diagnostic: why offline tools saw stale XAUUSD lake data (2026-07-14)

Read-only investigation. All claims below are backed by direct file reads,
`git log`, filesystem mtimes, and a read-only reproduction of the exact
loader function used by `scripts/live/check_live_sim_parity.py`. No repo
file was modified; no writer was run against the real lake. Machine
`data/lake/manifest.json` and JSON companion at
`scripts/report/diag_h4_lake.json`.

## System clock / timezone caveat

`ls -la --time-style=full-iso` reports file mtimes with a `-04:00` suffix
(system tzname: "Hora est. Sudamérica Pacífico"). Interpreting the same
mtime epoch value directly as UTC (`datetime.fromtimestamp(mt, timezone.utc)`
in Python) yields a value **4 hours later** than the `-04:00`-suffixed
display, and critically, 4 hours later than the UTC timestamps embedded in
the bar data itself inside the very same files (e.g. `XAUUSD/5.parquet`'s
mtime-as-UTC computes to `2026-07-14T11:53:59Z`, but that file's own last
bar row is timestamped `2026-07-14T07:50:00Z`). This document uses the
`-04:00` **display time** for all mtimes (the frame the orchestrator's
context — "02:54", "07:53" — was already anchored to), cross-checked
against bar-content timestamps wherever available (those are TZ-unambiguous
and independent of the system clock).

## 1. Write path

### `scripts/mt5_dump_history.py`

- Imports only `sentinel_engine.lake.ingest_mt5.ingest_mt5_csv` and
  `sentinel_engine.lake.manifest.{build_manifest, write_manifest}`
  (lines 34–35). It does **not** import `sentinel_engine.lake.tiers` or
  `scripts.build_tiers` anywhere.
- `main()` flow: for each of 16 symbols × 6 timeframes, `fetch_series()`
  pages MT5 history backward, `drop_forming_bar()` trims the trailing
  forming bar, `write_csv()` overwrites `data/raw/<lake_key>/<tf_min>.csv`
  (full overwrite each run, capped at ~100,000 rows by the fetch loop).
- After the fetch loop, lines 186–189:
  ```
  for lake_key, tf_min, path in csv_paths:
      ingest_mt5_csv(path, lake_key, tf_min, LAKE_ROOT, update_manifest=False)
  write_manifest(LAKE_ROOT, gap_tolerance_factor=3.0)
  ```
- `ingest_mt5_csv` (`sentinel_engine/lake/ingest_mt5.py:50-59`) reads the
  CSV and calls `write_bars(lake_root, symbol, timeframe_minutes, df)`.
- `write_bars` (`sentinel_engine/lake/store.py:29-59`) writes **only**
  `<lake_root>/<symbol>/<tf_minutes>.parquet` — the monolithic layer. It
  merges with any existing file (`pd.concat([existing, out])`, dedupe on
  index `keep="last"`, sort), which is why the monolith accumulates more
  rows across runs than a single raw CSV holds (e.g. `XAUUSD/5.parquet` has
  101,267 rows vs. the raw CSV's 100,000-row cap).
- `write_manifest` (`sentinel_engine/lake/manifest.py:82-90`) calls
  `build_manifest`, which does a **full fresh rescan** of
  `list_lake_entries(lake_root)` — i.e., every `<symbol>/<tf_minutes>.parquet`
  monolith file — and writes the whole `manifest.json` dict from scratch
  (it does not read or merge any pre-existing manifest.json content).

**Conclusion: `mt5_dump_history.py`'s entire call chain touches only the
monolithic `<symbol>/<tf_minutes>.parquet` layer and the flat
minute-integer-keyed `manifest.json`. It never calls `build_tiers` and never
writes to `<symbol>/<TF_NAME>/<YYYY-MM>.parquet`.**

### `sentinel_engine/lake/tiers.py` / `scripts/build_tiers.py`

- `build_tiers(symbol, lake_root, now_epoch=None)` (`tiers.py:174-231`) is
  the **only** function in the repo that writes
  `<lake_root>/<symbol>/<TF_NAME>/<YYYY-MM>.parquet` tier files (`TF_NAME`
  ∈ {M1, M2, M5, M15, H1, D}). It reads its source bars via
  `sentinel_engine.lake.store.read_bars` (the monolith reader), resamples,
  and writes monthly tier parquet files plus `TF_NAME`-keyed entries into
  `manifest.json` via `manifest.setdefault(symbol, {})[tf_name] = entry`.
- The only caller of `build_tiers` in the repo is `scripts/build_tiers.py`
  (CLI entrypoint, `--symbol` flag, manual/scheduled invocation — line 28:
  `report = build_tiers(symbol, args.lake_root)`).
- `git log --oneline` for both `sentinel_engine/lake/tiers.py` and
  `scripts/build_tiers.py` shows a single commit, `b776ed0` ("feat(a1):
  lake TF-tiers builder"), dated `2026-07-12 16:16:59 -04:00` — two days
  before this investigation, and no commits touch these files afterward.

**No code path invoked by `mt5_dump_history.py` updates the tiers.**

## 6. `drop_forming_bar` / stale `now_epoch` analysis

`scripts/mt5_dump_history.py:153`:
```python
now_epoch = int(datetime.now(timezone.utc).timestamp())
```
captured once, at the top of `main()`, **before** `mt5.initialize()` and
before the double loop over 16 symbols × 6 timeframes (up to 96
`fetch_series` calls, each itself paging up to 400 chunked
`copy_rates_from` calls). This single `now_epoch` value is passed unchanged
into every `drop_forming_bar(df, tf_min, now_epoch)` call for the entire
run (lines 87-98):

```python
def drop_forming_bar(df, tf_minutes, now_epoch):
    if df.empty:
        return df
    last_t = df.index[-1]
    t_epoch = int(last_t.timestamp())
    if t_epoch + tf_minutes * 60 > now_epoch:
        return df.iloc[:-1]
    return df
```

By construction this function only ever removes `df.iloc[:-1]` — at most
the **single trailing row** — regardless of how stale `now_epoch` is by the
time a given symbol/TF is fetched later in the loop. A stale (too-old)
`now_epoch` can only make the "still forming" check less aggressive over
time (worst case: a bar closed since `now_epoch` was captured is wrongly
kept, or a bar not yet closed at capture-time but closed by fetch-time is
still evaluated against the old `now_epoch` and could be incorrectly
dropped) — it cannot structurally cause loss of more than that one trailing
bar, and cannot cascade into discarding older, already-closed bars.

Empirically (section 5 above), the raw CSV max timestamps for XAUUSD
{1,2,5,15} exactly equal the monolith max timestamps, and no recent raw
bars are missing from the monolith — confirming no such discard actually
happened for XAUUSD in last night's run(s).

## Conclusion

The monolithic layer `data/lake/XAUUSD/{1,2,5,15,60,1440}.parquet` is
written by `scripts/mt5_dump_history.py` (via
`ingest_mt5.ingest_mt5_csv` → `store.write_bars`) and was last written at
`2026-07-14 07:53:58–07:53:59` (local display time), containing bars
through `07:53:00Z` / `07:52:00Z` / `07:50:00Z` / `07:45:00Z` for the
1/2/5/15-minute series respectively, exactly matching the corresponding raw
CSV exports (no forming-bar over-discard found). The tier layer
`data/lake/XAUUSD/{M1,M2,M5,M15,H1,D}/2026-07.parquet` is written **only**
by `scripts/build_tiers.py` (via `sentinel_engine.lake.tiers.build_tiers`),
which was last run at `2026-07-14 02:57:2x` (local display time) — roughly
five hours before the dump script's last run completed — and
`mt5_dump_history.py` contains no call into the tiers module at all.
`scripts/live/check_live_sim_parity.py`'s `load_bars()` (lines 103-135)
reads exclusively from the tier layer
(`lake_root/symbol/TF_NAME/YYYY-MM.parquet`); reproducing that exact
function read-only against the live lake for XAUUSD M5 returned a max bar
time of `2026-07-14T02:50:00+00:00`, matching the tier file's content
precisely, confirming the parity checker consumed the stale, un-rebuilt
tier layer while the monolith — five hours further ahead — sat unread by
that code path. No writer bug was found or demonstrated in `ingest_mt5_csv`,
`write_bars`, `drop_forming_bar`, or `tiers.py`'s resample logic; the
staleness is fully and exclusively explained by `scripts/build_tiers.py`
simply not having been re-invoked after `02:57`, not by any data loss or
discard in the write path.
